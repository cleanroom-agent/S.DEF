## Root Definition

### `SoftwareDefinition`

The root object of any S.DEF document.
Contains all layers of software description: system boundary, domain model,
architecture, data models, contracts, behavior, UI, tests, design decisions,
reconstruction rules, dependencies, and deployment requirements.

| Property               | Type                  | Required | Description                                                                     |
| ---------------------- | --------------------- | -------- | ------------------------------------------------------------------------------- |
| `sdef_version`         | `string`              | Yes      | Schema version (date-based, e.g. "2026-05-27").                                 |
| `name`                 | `string`              | Yes      | The software identifier (e.g. "com.example.todoapp").                           |
| `description`          | `string`              | No       | Human-readable description.                                                     |
| `version`              | `string`              | No       | Version of the software being described.                                        |
| `metadata`             | `SoftwareMetadata`    | No       | Metadata associated with the software.                                          |
| `system_boundary`      | `SystemBoundary`      | No       | System boundary — what the software does and does NOT do.                       |
| `design_decisions`     | `DesignDecision[]`    | No       | Design decisions with rationale.                                                |
| `version_history`      | `VersionRecord[]`     | No       | Version history — tracks the evolution of the software over time.               |
| `domain`               | `Domain`              | No       | Domain model — business concepts, rules, and processes.                         |
| `architecture`         | `Architecture`        | No       | Architecture — structural layers, modules, and communication patterns.          |
| `data_models`          | `DataModel[]`         | No       | Data model — entities, their attributes, relationships, and validation rules.   |
| `contracts`            | `Contracts`           | No       | Contracts — interfaces, classes, enums, and API endpoints.                      |
| `behavior`             | `Behavior`            | No       | Behavior — functions, flows, and state machines.                                |
| `ui`                   | `UserInterface`       | No       | User interface — screens, components, interactions, and navigation.             |
| `tests`                | `TestContract`        | No       | Test contracts — unit tests, integration tests, and acceptance criteria.        |
| `reconstruction_rules` | `ReconstructionRules` | No       | Reconstruction rules — fidelity target, technology constraints, and directives. |
| `dependencies`         | `Dependency[]`        | No       | External software dependencies (packages, services).                            |
| `deployment`           | `Deployment`          | No       | Deployment and runtime requirements.                                            |
| `resources`            | `Resource[]`          | No       | Resources the software provides or consumes.                                    |

## System Boundary

### `SystemBoundary`

Defines the scope of the software — what it does, what it explicitly does NOT do,
who the target users are, and the success criteria.
The `non_goals` field is a critical guardrail: it prevents a reconstruction agent
from over-implementing features that were intentionally excluded.

| Property                | Type           | Required | Description                                                        |
| ----------------------- | -------------- | -------- | ------------------------------------------------------------------ |
| `core_purpose`          | `string`       | Yes      | The core purpose of the software in one sentence.                  |
| `target_users`          | `string[]`     | No       | Target user personas.                                              |
| `in_scope`              | `string[]`     | No       | Features that are in scope.                                        |
| `non_goals`             | `string[]`     | No       | Features explicitly out of scope (prevents over-implementation).   |
| `success_criteria`      | `string[]`     | No       | Measurable success criteria (e.g. "page load < 200ms").            |
| `constraints`           | `Constraint[]` | No       | Constraints (performance, compatibility, security, accessibility). |
| `external_dependencies` | `string[]`     | No       | External dependencies at the system level (APIs, services).        |

### `Constraint`

| Property      | Type     | Required | Description                                                            |
| ------------- | -------- | -------- | ---------------------------------------------------------------------- |
| `category`    | `string` | Yes      | Constraint category (e.g. "performance", "compatibility", "security"). |
| `description` | `string` | Yes      | Constraint description.                                                |

## Design Decisions

### `DesignDecision`

A record of a design decision, its context, alternatives considered,
rationale, and consequences.
Every significant architectural or design choice should be captured here.

| Property       | Type       | Required | Description                                      |
| -------------- | ---------- | -------- | ------------------------------------------------ |
| `id`           | `string`   | Yes      | Unique identifier for this decision.             |
| `topic`        | `string`   | Yes      | The topic / area this decision applies to.       |
| `decision`     | `string`   | Yes      | The chosen approach.                             |
| `rationale`    | `string`   | Yes      | Why this approach was chosen.                    |
| `context`      | `string`   | No       | The context in which the decision was made.      |
| `alternatives` | `string[]` | No       | Alternatives that were considered.               |
| `consequences` | `string[]` | No       | Consequences (both positive and negative).       |
| `constraints`  | `string[]` | No       | Additional constraints imposed by this decision. |

## Versioning & Compatibility

### `VersionRecord`

A record of a software version, capturing what changed and how
backward compatibility was (or wasn't) maintained.
This enables consumer agents to understand the evolution of the software
and make informed decisions about which compatibility layers to include.

| Property              | Type       | Required | Description                                  |
| --------------------- | ---------- | -------- | -------------------------------------------- |
| `version`             | `string`   | Yes      | Version identifier (e.g. "1.0.0", "2.0.0").  |
| `release_date`        | `string`   | No       | Release date.                                |
| `deprecated`          | `boolean`  | No       | Whether this version is deprecated.          |
| `eol_date`            | `string`   | No       | When this version reaches end-of-life.       |
| `breaking_changes`    | `string[]` | No       | Breaking changes introduced in this version. |
| `compatibility_notes` | `string`   | No       | Notes on backward compatibility.             |

### `DeprecationInfo`

Deprecation metadata — marks an interface, class, data entity, or method
as superseded by a newer version.
Consumer agents use this to decide whether to generate the element:

- `include_compatibility: false` → skip all deprecated elements
- `include_compatibility: true` → generate with deprecation annotations

| Property          | Type     | Required | Description                                                                         |
| ----------------- | -------- | -------- | ----------------------------------------------------------------------------------- |
| `since_version`   | `string` | No       | Version in which this element was deprecated.                                       |
| `replaced_by`     | `string` | No       | Reference to the element that replaces this one (e.g. entity name or interface ID). |
| `removal_version` | `string` | No       | Version in which this element is planned (or was) removed.                          |
| `migration_guide` | `string` | No       | Guidance for migrating from this element to its replacement.                        |

### `CompatibilityMapping`

Compatibility mapping — describes how a legacy element (API, data field)
maps to the current version's equivalent.
This is used by consumer agents when generating adapter/forwarder code.

| Property          | Type                     | Required | Description                                            |
| ----------------- | ------------------------ | -------- | ------------------------------------------------------ |
| `maps_to`         | `string`                 | No       | The target element this one forwards to.               |
| `field_mapping`   | `Record<string, string>` | No       | Mapping of legacy field names to current field names.  |
| `transform_logic` | `string`                 | No       | Description of the transformation logic in pseudocode. |
| `bidirectional`   | `boolean`                | No       | Whether the mapping is bidirectional.                  |

### `DataMigration`

Data migration specification — describes how to convert data
from an older schema version to the current schema.

| Property       | Type     | Required | Description                                    |
| -------------- | -------- | -------- | ---------------------------------------------- |
| `id`           | `string` | Yes      | Unique identifier.                             |
| `description`  | `string` | No       | Description.                                   |
| `from_entity`  | `string` | Yes      | Source entity name (old version).              |
| `to_entity`    | `string` | Yes      | Target entity name (new version).              |
| `from_version` | `string` | No       | Source version.                                |
| `to_version`   | `string` | No       | Target version.                                |
| `algorithm`    | `string` | No       | Pseudocode describing the migration algorithm. |

## Domain Layer

### `Domain`

The Domain Layer describes the business problem domain — the concepts,
rules, and processes that the software models and automates.
This is the anchor for all other layers: code and data structures exist
to operate on these business concepts.

| Property             | Type                | Required | Description                                  |
| -------------------- | ------------------- | -------- | -------------------------------------------- |
| `business_concepts`  | `BusinessConcept[]` | No       | Business concepts — the nouns of the domain. |
| `business_rules`     | `BusinessRule[]`    | No       | Business rules — conditions and actions.     |
| `business_processes` | `BusinessProcess[]` | No       | Business processes — multi-stage workflows.  |

## Contracts

### `Contracts`

The Contracts section defines the interfaces, classes, enums,
and API endpoints that form the software's public contract.
This is the "contract-first" core: everything is described by its
input/output signatures, behavior, pre/post conditions, and error cases.

| Property                | Type                    | Required | Description                                                                   |
| ----------------------- | ----------------------- | -------- | ----------------------------------------------------------------------------- |
| `interfaces`            | `InterfaceContract[]`   | No       | Abstract interfaces.                                                          |
| `classes`               | `ClassContract[]`       | No       | Concrete classes.                                                             |
| `enums`                 | `EnumContract[]`        | No       | Enumerations.                                                                 |
| `apis`                  | `ApiContract[]`         | No       | API endpoints (REST, gRPC, etc.).                                             |
| `compatibility_modules` | `CompatibilityModule[]` | No       | Compatibility modules — isolated modules that exist only for backward compat. |
| `data_migrations`       | `DataMigration[]`       | No       | Data migration specifications.                                                |

### `CompatibilityModule`

A compatibility module is an isolated set of interfaces, classes, or APIs
that exist solely to maintain backward compatibility with older versions.
Consumer agents can optionally exclude these when generating clean code.

| Property           | Type       | Required | Description                                          |
| ------------------ | ---------- | -------- | ---------------------------------------------------- |
| `id`               | `string`   | Yes      | Module identifier.                                   |
| `name`             | `string`   | Yes      | Human-readable name.                                 |
| `description`      | `string`   | No       | Description.                                         |
| `targets_versions` | `string[]` | No       | The versions this module provides compatibility for. |
| `interfaces`       | `string[]` | No       | Interfaces in this compat module.                    |
| `functions`        | `string[]` | No       | Functions in this compat module.                     |

### `InterfaceContract`

| Property      | Type               | Required | Description                                                   |
| ------------- | ------------------ | -------- | ------------------------------------------------------------- |
| `name`        | `string`           | Yes      | -                                                             |

## Reconstruction Rules

### `ReconstructionRules`

Reconstruction Rules guide the builder agent in how to reconstruct
the software from the S.DEF description.
This includes the target fidelity level, technology stack constraints,
and priority-ordered directives.

| Property                   | Type                                       | Required                                                                                                                                                                                                      | Description                                                                                                                                                                                                                                                                                                      |
| -------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reconstruction_fidelity`  | `\| "prototype"                            |
| \| "production_equivalent" |
| \| "bit_identical"`        | No                                         | Target reconstruction fidelity: - "prototype": Functional demo, fidelity not guaranteed - "production_equivalent": Functionally equivalent, similar quality - "bit_identical": Byte-for-byte identical output |
| `compatibility_mode`       | `"full" \| "mixed" \| "clean" \| "custom"` | No                                                                                                                                                                                                            | Compatibility mode for code generation: - "full": Keep all compatibility layers (behavior identical to original) - "mixed": Keep compat layers but mark as deprecated - "clean": Strip all deprecated/compat elements, generate only current versions - "custom": Use `target_versions` for fine-grained control |
| `target_versions`          | `string[]`                                 | No                                                                                                                                                                                                            | When compatibility_mode is "custom", which versions to include compat for.                                                                                                                                                                                                                                       |
| `tech_constraints`         | `TechConstraints`                          | No                                                                                                                                                                                                            | Technology stack constraints.                                                                                                                                                                                                                                                                                    |
