# PROPOSAL-{NUMBER}: {Title}

> **Note**: This template provides a standard structure for S.DEF Enhancement Proposals. Adapt sections based on the specific needs of your proposal.

- **Status**: Draft | In-Review | Accepted | Rejected | Withdrawn | Final | Superseded | Dormant
- **Type**: Standards Track | Informational | Process
- **Created**: YYYY-MM-DD
- **Author**: Name <email> (@github-username)
- **Sponsor**: @github-username (or "None" if seeking sponsor)
- **PR**: https://github.com/cleanroom-agent/S.DEF/pull/{NUMBER}

## Summary

Brief (~200 word) technical summary of the proposal. This should be a concise overview that allows readers to quickly understand what this proposal changes.

## Motivation

Why is this change needed? Why is the current specification inadequate to address the problem that this proposal solves?

Proposals without sufficient motivation may be rejected outright.

## Specification

Detailed technical specification of the proposed changes. The specification should describe the syntax and semantics of any new feature in sufficient detail to allow competing, interoperable implementations.

For Schema changes, include:

- New or modified type definitions
- Required vs optional fields
- Validation constraints
- Usage examples

For Process changes, include:

- Step-by-step procedures
- Roles and responsibilities
- Timelines or milestones

## Rationale

Explain why particular design decisions were made. This section should:

- Describe alternate designs that were considered
- Explain why the proposed approach was chosen
- Reference related work or prior art
- Document important objections or concerns raised during discussion

## Backward Compatibility

**Required for proposals that introduce backward incompatibilities.**

Describe:

- What existing S.DEF documents will break or change
- The severity and scope of incompatibilities
- Migration paths for existing documents

If there are no backward compatibility concerns, state that explicitly.

## Security Implications

Describe any security concerns related to this proposal, including:

- New attack surfaces
- Privacy considerations
- Data validation requirements

If there are no security implications, state that explicitly.

## Reference Implementation

Link to or describe a reference implementation. A reference implementation is required before any proposal can be given "Final" status.
